# Nirmitee PAS Server Contract (Da Vinci PAS 2.2.1 and 2.0.1)

Behavior contract for the Nirmitee Prior Authorization Support (PAS) payer servers, implemented twice (Go and
.NET) with identical observable behavior. Acceptance criteria: zero failures (and zero skips) in the Inferno
**Da Vinci PAS Server** suites `davinci_pas_server_suite_v221` and `davinci_pas_server_suite_v201`.

Source of truth, in order:
1. The Ruby tests in `davinci-pas-test-kit` 0.15.2 (`lib/davinci_pas_test_kit/server/**`, `cross_suite/**`,
   `pas_notification_conformance_test.rb`), inferno_core 1.4.3, subscriptions_test_kit 0.12.2.
2. Da Vinci PAS IG 2.2.1 and STU 2.0.1, Subscriptions R5 Backport 1.1.0.

File citations below are relative to `davinci-pas-test-kit/lib/davinci_pas_test_kit/` unless they start with
`subscriptions_test_kit/` or `inferno_core/`.

Companion files (paths relative to the repository root):

| File | Purpose |
|---|---|
| `spec/adjudication-rules.json` | Deterministic decision rules both servers load unchanged (section 6) |
| `spec/ms-metadata/v221.json`, `v201.json` | Must support metadata exported from the kit (section 10) |
| `spec/examples/<version>/*.json` | Canonical example payloads generated by the reference model |
| `spec/reference/pas_reference.py` | Executable reference model: replays the testdata in suite order, writes the examples, runs offline checks |

## 0. Architecture note

- PAS is a **separate deployable server** (own port, Dockerfile, README), designed to **merge later** into a
  combined burden reduction server together with CRD and DTR.
- Go: package `pas` exposing `NewHandler(cfg) http.Handler`, no global state; host binary `cmd/pas-server`;
  shared concerns (auth, FHIR JSON helpers, audit log, config) in the shared internal package.
- .NET: class library `Nirmitee.DaVinci.Pas` exposing `services.AddPas(config)` and `endpoints.MapPas(prefix)`;
  host project `Nirmitee.DaVinci.Pas.Host`; shared `Nirmitee.DaVinci.Common`.
- All routes are relative to a configurable prefix (standalone default: empty). No absolute paths or ports
  inside the library. The FHIR base URL used inside notifications (`Subscription/{id}` references, `$status`
  URLs) is derived from configuration `PAS_PUBLIC_BASE_URL` when set, else from the incoming request
  (scheme, host, port, prefix).

## 2. What the suites test

Inferno acts as the PAS client. It sends tester supplied Bundles (our `testdata/`) and checks the responses.
Every request made in a test is tagged and reused by later tests (`cross_suite/tags.rb`), so must support
checks aggregate over the whole session. Run the groups in order.

## 3. Transport, authentication, CapabilityStatement

- Requests from Inferno: `POST` with `Content-Type: application/fhir+json` (inferno_core FHIR client). Accept
  `application/fhir+json` and `application/json`. Respond with `Content-Type: application/fhir+json; charset=utf-8`.
- `$submit` returns **200** (not 201): the no custom extensions test only inspects requests whose status is 200
  (`v2.2.1/pas_server_no_custom_extensions_test.rb` line 188). `$inquire` returns 200.
- Response time: warning above 15 s (`claim_operation_logic.rb` line 31). Target under 2 s.
- **Auth**: the `smart_credentials` input is optional and the suite does not score OAuth
  (`docs/Server-Details.md` "Authentication"). When `PAS_AUTH_TOKENS` is empty no auth is required. When set,
  every FHIR route except `GET /metadata` requires `Authorization: Bearer <token>` from the list; otherwise
  respond 401 with `WWW-Authenticate: Bearer` and an OperationOutcome (`security`). The harness passes
  `--bearer-token` as the OAuth Credentials input. Subscription creation uses the same auth
  (`docs/Server-Details.md` "Subscription").
- Unknown route: 404 OperationOutcome (`not-found`). Wrong method: 405 OperationOutcome (`not-supported`).

create, update, delete; full example `spec/examples/v221/metadata.json`):

## 4. Claim/$submit

### 4.1 Request validation (400)

Return **400** with an OperationOutcome (no ClaimResponse) when the body cannot be processed
(`v2.2.1/error_tests/pas_submission_error_test.rb`, IG: "the receiving system SHALL return OperationOutcome
instances that detail why the Bundle could not be processed"):

| Condition | issue.code | expression |
|---|---|---|
| body not JSON or not a Bundle | `structure` | `Bundle` |
| `Bundle.type` not `collection` | `invalid` | `Bundle.type` |
| `Bundle.entry` empty (the kit's error test) | `required` | `Bundle.entry` |
| first entry not a Claim | `invalid` | `Bundle.entry[0].resource` |
| `Claim.patient`, `Claim.insurer` or `Claim.provider` not resolvable in the Bundle | `invalid` | `Claim.patient` etc. |
| `Claim.item` missing | `required` | `Claim.item` |

```json
{
  "resourceType": "OperationOutcome",
  "issue": [{
    "severity": "error",
    "code": "required",
    "details": { "text": "The PAS Bundle has no entries; the first entry must be a Claim." },
    "diagnostics": "The PAS Bundle has no entries; the first entry must be a Claim.",
    "expression": ["Bundle.entry"]
  }]
}
```

Do **not** reject on profile validation, unknown extensions, X12 codes or must support gaps: the tester
Bundles are validated by Inferno, not by the server. Business problems go into `ClaimResponse.error` (4.6).

### 4.2 Processing

1. Adjudicate each `Claim.item` with `adjudication-rules.json` (section 6).
2. Store a claim record keyed by `Claim.identifier[0].system|value`: the Claim, the request Bundle, the Claim
   entry fullUrl and the per item results. A later submit with the same identifier replaces the record (Claim
   updates, section 8).
3. Schedule auto finalize for items whose rule has `autoFinalize: true` (section 7.3).
4. Return 200 with a PAS Response Bundle.

### 4.3 Response Bundle structure (`cross_suite/pas_bundle_validation.rb`)

| Rule | Source |
|---|---|
| `resourceType` Bundle, `type` `collection`, `timestamp` now, `identifier` `{ "system": "urn:ietf:rfc:3986", "value": "urn:uuid:<uuid>" }` (min 1 in 2.2.1), `meta.profile` unversioned `profile-pas-response-bundle` | IG profile, response generator in `client/response_generator.rb` |
| **First entry is the ClaimResponse**, fullUrl `urn:uuid:<id>` | `validate_pa_response_body_structure` |
| **Every Reference.reference in the response equals the fullUrl of an entry of the response Bundle**, verbatim. Do not use relative references (the kit derives the base URL from the *last* entry's fullUrl, which is often a `urn:uuid`) | `check_presence_of_referenced_resources`, `extract_base_url` |
| Every resource referenced from the ClaimResponse (except `ClaimResponse.request`), and transitively from those, appears **exactly once** | same |
| Resources echoed from the request keep the **same fullUrl, id and identifier** as in the request (copy them verbatim) | `validate_echoed_response_resources` |
| Never include the submitted Claim (not required, and it would drag its references in) | `claim_response_request_attr?` |
| Generated resources (CommunicationRequest, Task) use `urn:uuid` fullUrls | examples |

Entry order used by the reference model: ClaimResponse, then references in the order they are met, then
CommunicationRequest (if not already reached), then Task.

## 5. Claim/$inquire

### 5.1 Validation

Same 400 rules as 4.1, except the Claim may be any entry and `Claim.item` is optional
(`v2.2.1/error_tests/pas_inquiry_error_test.rb`, `pas_bundle_validation.rb` inquiry checks).

### 5.2 Matching and response

1. Look up the stored record by `Claim.identifier[0].system|value`.
2. For each inquiry `Claim.item`, take the stored result with the same `sequence`; if none (or no record), adjudicate
   that inquiry item with the rules (stateless fallback, so results never depend on test order).
3. Build a PAS Inquiry Response Bundle exactly like 4.3 and 4.4 with these differences: `meta.profile`
   `profile-pas-inquiry-response-bundle` and `profile-claiminquiryresponse`; no `communicationRequest`;
   references may resolve against the inquiry Bundle **and** the stored submit Bundle (for addItem
   requestedService); `request` = the stored Claim fullUrl when a record exists and that URL is absolute,
   otherwise the data-absent-reason extension (spec-44).
4. **v2.2.1**: wrap in Parameters with parameter name **`return`** (the kit reads `return`; the IG example uses
   `responseBundle`, the kit wins) (`parameters_helper.rb`, `claim_operation_logic.rb` line 47).
   **v2.0.1**: return the Bundle itself.

```json
{
  "resourceType": "Parameters",
  "parameter": [ { "name": "return", "resource": { "resourceType": "Bundle", "type": "collection", "entry": [ "..." ] } } ]
}
```

### 5.3 Replaced authorization numbers (spec-47, v2.2.1 test, applied in both versions)

When an inquiry item carries `extension-authorizationNumber` whose value is a key of
`replacedAuthorizations`, the response item carries `extension-authorizationNumber` with the mapped (current)
value, and the reviewAction `number` is that value when certified. Other values are echoed.
Example: `AUTH-PA-2026-0004-1` becomes `AUTH-PA-2026-0004-1-R1`.

## 7. Subscriptions and the pended flow

### 7.1 Subscription create, read, update, delete

`POST /Subscription` (inferno sends the input after `server_check_channel`, `subscriptions_test_kit/common/subscription_conformance_verification.rb`):

- Accept when `criteria` is `http://hl7.org/fhir/us/davinci-pas/SubscriptionTopic/PASSubscriptionTopic`,
  `channel.type` is `rest-hook`, `channel.endpoint` is present and the backport payload content is `full-resource`
  or `id-only`. Otherwise 422 OperationOutcome (`business-rule`).
- Respond **201** with the stored Subscription: server assigned `id`, **`status` `requested`**, everything else as
  sent (including `channel.header`), `Location: <base>/Subscription/<id>` (`creation_response_conformance_test.rb`).
- Store `channel.endpoint`, `channel.payload`, `channel.header[]` and the filter
  (`backport-filter-criteria` `org-identifier=<value>`).
- Then send the handshake (7.2). After a 2xx handshake answer set `status` `active`.
- `GET /Subscription/{id}` returns it; `PUT` replaces it (same validation, 200); `DELETE` removes it (200 or 204);
  unknown id 404. `GET /Subscription/{id}/$status` returns the SubscriptionStatus Parameters (7.2 shape, type
  `query-status`).

### 7.2 Handshake (`handshake_conformance_test.rb`, `notification_conformance_verification.rb`)

POST to `channel.endpoint` with every `channel.header` entry sent as an HTTP header (`name: value`, split on the
first `": "`) and `Content-Type: <channel.payload>` (default `application/fhir+json`). Send about 1 s after the 201,
never synchronously inside the create request.

```json
{
  "resourceType": "Bundle",
  "type": "history",
  "timestamp": "2026-09-12T10:00:00Z",
  "entry": [{
    "fullUrl": "urn:uuid:38d2a998-6efa-4fb6-a42d-892459876284",
    "resource": {
      "resourceType": "Parameters",
      "parameter": [
        { "name": "subscription", "valueReference": { "reference": "http://host.docker.internal:8085/v221/fhir/Subscription/4827e031-9222-4699-aac8-300abc19e8d4" } },
        { "name": "topic", "valueCanonical": "http://hl7.org/fhir/us/davinci-pas/SubscriptionTopic/PASSubscriptionTopic" },
        { "name": "status", "valueCode": "requested" },
        { "name": "type", "valueCode": "handshake" },
        { "name": "events-since-subscription-start", "valueString": "0" }
      ]
    },
    "request": { "method": "GET", "url": "http://host.docker.internal:8085/v221/fhir/Subscription/4827e031-9222-4699-aac8-300abc19e8d4/$status" },
    "response": { "status": "200" }
  }]
}
```

Rules: Bundle `type` history; first entry Parameters valid against backport-subscription-status-r4 in the order
shown; every entry has `request` and `response`; `request.url` ends with `Subscription/<id>/$status`; the last path
segment of the `subscription` reference is the Subscription id (Inferno tags the request with it,
`subscriptions_test_kit/endpoints/subscription_rest_hook_endpoint.rb`); `status` `requested`; `type` `handshake`.

### 7.3 Finalize and event notification timing

- A pended item with `autoFinalize: true` is finalized `PAS_PENDED_AUTO_FINALIZE_SECONDS` after the submit, or
  immediately by `POST /admin/pended/finalize`. Finalize is idempotent. It flips the item to `finalDecision`,
  rebuilds the stored ClaimResponse (4.4, same Claim) and queues one event notification per active Subscription
  whose filter matches (`org-identifier=<v>` matches any `identifier.value` of the requestor Organization; a
  Subscription without filter matches everything).
- **Retry contract**: Inferno answers **500** when no test is waiting for that bearer token and **200** when it
  accepted the notification (`inferno_core/dsl/suite_endpoint.rb` `no_session_response`). Retry every
  `PAS_NOTIFICATION_RETRY_SECONDS` while the answer is not 2xx, for at most `PAS_NOTIFICATION_MAX_SECONDS`
  (Inferno wait timeout is 300 s, `inferno_core/dsl/results.rb` `wait`). After one 2xx, never resend that notification.
- **Never send heartbeats or duplicate notifications**: the pended wait test resumes on the first request with the
  token, whatever its type (`abstract_pas_subscription_notification_wait_test.rb`, the endpoint `update_result`
  passes any request because the test does not accept multiple requests). A stray handshake retry during the pended
  wait would resume it with no event notification and the conformance tests would skip.
- The Subscription Setup wait (1.03) accepts multiple requests and is resumed by the harness through the
  confirmation URL (section 15), so the handshake can be received any time during that wait.

### 7.4 Event notification

v2.2.1 `full-resource` (`full_resource_conformance_test.rb`, `pas_notification_verification.rb`): second entry is the
**updated PAS Response Bundle** (same content rules as 4.3 and 4.4), fullUrl `urn:uuid:<response bundle id>`, focus
references that fullUrl.

**Notification copy rule.** The full-resource test re-validates the nested ClaimResponse. The kit's validator
suppressions for IG extension context defects are anchored to top level element paths (for example
`(this element is [ClaimResponse]`), so they do not match inside `Bundle.entry.resource` and the errors surface

`extension-certificationType`. Must support is not affected: the notification is not tagged as a `$submit` response.

## 11. Control endpoints (test automation only)

These routes exist only so an Inferno run can proceed without a human. They reveal notification contents and bearer
tokens and let the caller decide pended claims, so they are **disabled by default**:

- Enabled only when the environment variable `PAS_ADMIN_ENABLED` is exactly `true`. Any other value, or no value,
  disables them.
- When disabled, every `/admin/*` path answers **404** with an OperationOutcome (`not-found`), exactly like an unknown
  route, so a deployment does not reveal that they exist.
- When enabled, requests that carry `X-Forwarded-For` or `Forwarded` headers (for example through a tunnel or reverse
  proxy) are still rejected with 403; the harness calls them directly on the server host.
- Never enable them on a deployment reachable from the internet, except for the duration of an Inferno run, and turn
  them off again afterwards (restart without the flag). Production and published container images must not set it.
- `GET {prefix}/health` is not an admin route and stays available.

| Route | Behavior when enabled |
|---|---|
| `POST {prefix}/admin/pended/finalize` | optional body `{ "version": "v221" }`; finalizes every auto-finalizable pended item now and queues notifications; 200 `{ "finalized": ["<ClaimResponse id>"], "notifications": 1 }` |
| `POST {prefix}/admin/reset` | clears claims, subscriptions and outbox; 204 |
| `GET {prefix}/admin/notifications` | 200 `{ "notifications": [ { "version": "v221", "kind": "handshake", "subscription_id": "...", "endpoint_token": "<bearer token sent to the endpoint>", "attempts": 1, "status": 200, "delivered": true, "queued_at": "2026-09-12T07:47:21Z" } ] }`: delivery log of handshake and event notifications. The harness polls it to confirm the Subscription Setup wait (Inferno does not expose the incoming handshake on the waiting result, confirmed live) |
| `GET {prefix}/health` | 200 `{ "status": "ok" }` (always on) |

Without the flag an Inferno run still completes but more slowly: the harness waits `--handshake-grace` seconds at the
handshake and relies on auto finalize (`PAS_PENDED_AUTO_FINALIZE_SECONDS`) at the pended wait.

   previousAuthorizationNumber in the profile) because that is what spec-47's test compares.
4. `Claim.accident` is populated on the must support Bundles only because it is must support; it is not clinically
   meaningful for these DME requests.
5. Harness behavior against Inferno (resolved live, kit 0.15.2, inferno_core 1.4.3 local and 1.4.4 public):
   the incoming handshake is persisted but not exposed on the waiting result through the JSON API, so the harness uses
   `GET /admin/notifications` (section 11); inferno.healthit.gov accepts scripted `POST /api/test_sessions` for both PAS
   server suites and its notification listener answers 500 when no test waits; bearer token handling is recorded in
   section 17.
6. Subscriptions from earlier sessions also receive notifications and get 500 answers until the retry window ends;
   call `POST /admin/reset` between harness runs.
